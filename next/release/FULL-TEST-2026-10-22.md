Test of commit `e55b45c` (HEAD: page-editor font fix `5035c77` + one top row `e55b45c`), run from a clean worktree.
**The app was built with `pnpm build:site` and served under `/app/` next to a copy of the website** (`waraq-site-1.0/.stage`, the folder the ZIP is made from), with the website's `_redirects` and `_headers` (the CSP) applied the way Cloudflare Pages does (clean URLs, 301 for `/app`). ## Run-time files (the `/app/` bug class)
- Every one of the 36 files of the build is fetched with status 200 under `/app/`, with the website CSP in force (`script-src 'self' 'wasm-unsafe-eval'; worker-src 'self' blob:; font-src 'self' data:` …).
- During all 203 checks (editor fonts, OCR engine and language data, wasm, workers, the logo) the server log has **no 404 or other non-200** except the intended `301 /app → /app/`, and the browser reported **no CSP violation and no failed request**.
- `/support` and `/support.html` are 200 on the composed site (clean URL). The app itself has no link to it (finding 1).

## Failures and observations, most serious first

**1. (Medium) No "Report a problem" anywhere in the web app.** Steps: open the app, look at the start screen and every task. Expected (brief item 15, PLAN row C): a Help / ⋯ item "Report a problem" opening `/support` with version, OS and language filled. Found: no support link, and the crash-report buttons (Copy crash report / Open crash log folder) are desktop-only. The site has the page (`/support`, 200) and the release notes point to it, so a user inside the app has no way to reach it. (Rows "support / …": FAIL in EN and AR.)

**2. (Low, intermittent) Uncaught `TypeError: Cannot read properties of null (reading 'replaceChildren')`.** Seen in 2–3 groups of every run, English and Arabic, with no visible effect: after Save, or when a different document is opened right after another, while the viewer is still loading a page's text. Cause found in the source: `src/components/Viewer.svelte:91` — `loadText()` awaits the engine and then does `p.text.replaceChildren(frag)`; if the viewer was replaced during the await, `p.text` is `null`. Suggested fix (not applied, as asked): `if (!p.text) return` after the `await`. The test names the check that was running when the error fired, not necessarily the cause (the "organize" and "redact" rows).

**3. (Low, by design?) Recent cannot reopen a file on the web.** Steps: open `three.pdf` with the Open button, Close, click its card in Recent. Expected: it opens. Found: "This file is no longer where it was. Open it again." (EN and AR). The web build keeps no handle for a file chosen through the file chooser; portfolios reopen fine from Recent. Worth one line in the notes, or a "choose the file again" wording.

**4. (Note) Comment: the first Undo after typing a sticky-note text undoes the text, not the note.** Steps: add a text box and a sticky note with text, click Undo once: the count stays 10; the second click removes the note (10 → 9). Redo, Save, reopening and deleting one comment all work.

**5. (Note) Crash dialog.** After the simulated unclean exit the restore offer, Restore (the draft opens with the deleted page still deleted) and the crash-report Preview all work in EN and AR, and nothing was sent outside the site (every request was watched). A real process kill cannot be made from a browser test: closing a tab runs the app's own `pagehide`, which counts as a clean exit, so the test sets the app's "run that never said goodbye" marker the way `recovery.spec.ts` does.

**6. (Test-script bug, fixed in this run) Tauri smoke probe out of date.** `tools/dev/win-shot.ps1` sampled the old two-row bar (pixels at y = 12 / 24 / 38 and a left-edge column down to y = 60), so after `e55b45c` (logo and title in the top row, window buttons in the same row) every run failed on pixels that are the logo, the title and the bar's border. The probe now checks the flat strip above the row (y 0–8 at x = 24, 200, centre, and the left edge) and the page. Looking at the screenshot: the thin line under the top row stops before the window buttons (minimise / maximise / close): cosmetic, not a failure.

**7. (Test limits, honest list)** Not driven from a browser test: the real operating-system file dialogs (file choosers are answered with fixtures; the Open button is really clicked), a real drag from Explorer (a drop event with a real `File` is dispatched on the start screen), a real process kill (see 5), a physical touch screen, the Office/CAD converters (the web shows the "desktop only" note; the packs were tested in the release check), and Edge's and Acrobat's own copy of Waraq-written mixed lines.
